Decision matrix across every major architectural layer. Recommended choices reflect license, runtime, and integration constraints discussed in context.

Layer 01 — Backend API

API Gateway / HTTP Framework

Hono
Edge-native, lightweight, universal
14 KB, runs on Cloudflare Workers, Bun, Deno, Node, AWS Lambda. Used for the UniverseML metadata API, Payload extensions, and any edge-deployable routes.
PROS
  • Runs everywhere — edge, serverless, Node
  • Drizzle + Zod integrate cleanly
  • Type-safe RPC mode (no codegen)
  • Sub-5ms cold starts on edge
CONS
  • No DI container — needs discipline at scale
  • No native WebSocket gateway
  • No built-in MQTT transport
  • Large teams need enforced conventions
MITFree
NestJS
Enterprise, DI-based — RMM service only
Node-only, Angular-inspired DI container. Right choice specifically for the RMM telemetry/command service: MQTT transport, WebSocket gateways, CQRS, BullMQ all native. Not for edge deployment.
PROS
  • Native MQTT, gRPC, WebSocket transports
  • CQRS + Event Sourcing module built-in
  • DI makes Drizzle repos clean to inject
  • Large ecosystem of tested modules
CONS
  • Node-only, no edge/serverless
  • 500–2000ms cold starts on Lambda
  • Heavy boilerplate per feature
  • Overkill for simple REST endpoints
MITFree
FeathersJS v5 (Dove)
Service-oriented, automatic REST + WebSocket, hooks
Define a service, get REST and WebSocket exposure simultaneously — no separate controller or socket event code. Before/after/around hooks are transport-agnostic. Channels let you broadcast events only to specific clients (workspace isolation). Feathers client works on React Native. Built-in MongoDB and Knex adapters in v5 core.
PROS
  • One service → REST + WebSocket auto-wired
  • Channels: per-workspace real-time isolation
  • Feathers client: Expo subscriptions to service events
  • Transport-agnostic hooks cleaner than NestJS RxJS pipes
  • Less ceremony than NestJS for CRUD + real-time
CONS
  • No official Drizzle adapter — custom services required
  • No native MQTT transport (still need NestJS for that)
  • No edge/serverless deployment
  • Smaller community and ecosystem than NestJS
  • SQL still requires migrations (claim of "no migrations" only true for MongoDB)
MITFree
Fastify
High-performance Node alternative
Faster than Express, schema-based validation, plugin system. A middle ground if NestJS feels too heavy but Hono too minimal. Not edge-native.
PROS
  • Faster than Express in benchmarks
  • Built-in JSON schema validation
  • Familiar for Express developers
CONS
  • Node-only like NestJS
  • No edge/serverless native story
  • No native WebSocket or real-time story
MIT
Decision: Hono for all UniverseML API, metadata engine, and Cloudflare-deployed routes. NestJS for MQTT telemetry ingestion (native transport adapter required). FeathersJS is the strongest contender for the RMM management-plane service — device CRUD, alert management, and dashboard real-time push — where automatic REST+WebSocket dual exposure and the Feathers client on Expo reduce code significantly. If Drizzle is written as custom Feathers services (losing auto-CRUD), the channel system and client library still justify it over Hono for real-time surfaces. The MQTT ingestion layer still needs NestJS regardless.

Layer 02 — Management Plane / CMS

Content & Entity Management Framework

Payload CMS
Code-first, TypeScript, MIT licensed
Full TypeScript, Drizzle ORM under the hood, Local API (zero-latency server-side calls), built-in Jobs Queue, hooks at every lifecycle point. Management plane for stable, code-defined schemas: user accounts, device registry, alert rules, course catalog, CRM records.
PROS
  • MIT license — no BSL/AGPL contamination
  • Drizzle already in stack, no new ORM
  • beforeChange / afterChange hooks native
  • Jobs Queue with Postgres persistence
  • Beautiful admin UI out of the box
  • Local API for server-side zero-latency calls
CONS
  • Code-first only — no runtime user-defined schema
  • Schema changes require redeploy
  • Forking to add runtime schema = rewrites core
  • Community support only (no paid tier)
MITFree
Directus
Runtime schema, visual data model, flows
Runtime /collections + /fields + /relations API — user-defined schema without code changes. Visual data model editor. Flows automation. Strong integration story. The closest existing tool to the UniverseML metadata engine concept.
PROS
  • Runtime schema via REST API — no redeploy
  • Flows: event hooks, cron, webhooks
  • Robust REST + GraphQL auto-gen
  • Free under $5M total org finances
CONS
  • BSL 1.1 — $5M threshold triggers paid license
  • No off-the-shelf block hours support
  • Enterprise support = custom quote only
  • No mobile / React Native component story
BSL 1.1Free <$5M
NocoBase
Plugin-based no-code platform
Closest to the FileMaker-style ERD → UI generation vision. SchemaComponent pattern: the same Collection can render as TableBlock, FormBlock, KanbanBlock, CalendarBlock. 80+ plugins. Architecture validation — not suitable for direct adoption.
PROS
  • Proves the ERD→UI architecture works at scale
  • Plugin registry pattern to study/replicate
  • SchemaComponent decouples data from UI type
CONS
  • AGPL-3.0 — network copyleft for SaaS
  • Web-only (React/Koa), no React Native
  • Commercial plugins require paid license
AGPL-3.0
Decision: Payload for all stable-schema management planes (UniverseML user/workspace/billing, Digiguide content, RMM device registry). Build a custom metadata engine (Phase 1 of build plan) in Hono + Drizzle for runtime user-defined ERD — this is what Directus does natively, but under your own MIT-compatible code. Use Directus as the reference implementation to study, not depend on.

Layer 03 — ORM & Database

Data Access Layer

Drizzle ORM
TypeScript-first, SQL-like, lightweight
Already in the stack. SQL-like query builder with full TypeScript inference. Works with Payload, Hono, and NestJS. pgroll-compatible migrations.
PROS
  • Already chosen — no switching cost
  • Payload uses Drizzle natively
  • Lightweight bundle, no reflection magic
  • drizzle-zod generates Zod schemas from tables
CONS
  • Less mature than Prisma for complex relations
  • TimescaleDB hypertables need raw SQL
  • No official NocoBase/Directus adapter
Apache 2.0Free
TimescaleDB
Postgres extension for time-series
Postgres extension — stays in your existing Postgres instance. Continuous aggregates, retention policies, compression. Right tier for RMM telemetry (device metrics over time). JOIN-able with device metadata in single queries.
PROS
  • Stays in Postgres — one database vendor
  • JOIN time-series + relational in one query
  • Continuous aggregates for dashboard charts
  • Compression to ~10% of raw storage
CONS
  • Timescale License (free self-hosted, paid cloud)
  • Some features need TimescaleDB Cloud
  • Drizzle requires raw SQL for hypertable features
Timescale LicenseFree self-host
VictoriaMetrics
Purpose-built time-series, Prometheus-compatible
Single binary, MIT licensed, Prometheus-compatible. Better pure metrics performance than TimescaleDB. Separates metrics from your relational data — good if you want strict isolation.
PROS
  • MIT license, single Go binary
  • Better read performance for pure metrics
  • Prometheus ecosystem compatible
CONS
  • Separate database to operate
  • No SQL JOIN with device metadata
  • Extra infrastructure vs TimescaleDB extension
MITFree

Layer 05 — Offline Sync

Client-Side Data Sync Engine

PowerSync
Bidirectional SQLite sync, offline-first
Already integrated in Digiguide. Bidirectional, works with existing Drizzle schema, offline SQLite writes sync back to Supabase. Keep for user-owned data needing full offline write capability.
PROS
  • Already in production in Digiguide
  • Bidirectional — writes offline, syncs back
  • @powersync/drizzle-driver native integration
  • Schema-aware partial sync per workspace
CONS
  • Paid tiers for production scale
  • More complex than read-only sync needs
SaaSFree dev tier
Electric SQL + TanStack DB
Read-path sync + reactive client store
Electric serves Postgres shapes (filtered live views) to clients. TanStack DB is the reactive client store (sub-millisecond live queries). Simpler model for read-heavy metadata sync. Expo and web starters available.
PROS
  • Shape model ideal for metadata sync
  • TanStack DB unifies web + mobile store
  • PowerSync adapter — compatible with existing
  • Simpler for read-heavy derived data
CONS
  • Read-path only — writes still go through API
  • Less mature than PowerSync for production
  • Adds another sync abstraction to maintain
Apache 2.0Free
Decision: PowerSync for Digiguide's existing offline-write data and UniverseML canvas state. Evaluate Electric + TanStack DB for new UniverseML metadata sync (read-heavy, shape-filtered per workspace). Both can coexist — TanStack DB has a PowerSync adapter.

Layer 07 — Workflow Automation

Triggers, Workers & Business Logic

Payload Jobs Queue
Postgres-backed, durable, typed
Postgres-backed durable job queue. afterChange hooks → jobs.queue() pattern. Retry semantics, tracked in admin UI, cron scheduling. Right for management-plane business logic: billing triggers, onboarding sequences, alert evaluation.
PROS

  • Jobs tracked in Postgres admin UI
  • Typed tasks with Zod input schemas
  • Cron scheduling native
CONS
  • Not suited for high-throughput (1000s/min)
  • Postgres polling — higher latency than Redis queue
MITFree
BullMQ (NestJS)
Redis-backed, high-throughput, priority queues
Redis-backed via @nestjs/bullmq. Handles millions of jobs/day. Right for RMM telemetry processing pipeline — thousands of device check-ins per minute, alert condition evaluation, patch status ingestion.
PROS
  • Handles millions of jobs per day
  • Priority queues, rate limiting, deduplication
  • Concurrency control per worker pool
  • @nestjs/bullmq first-class integration
CONS
  • Redis dependency to operate
  • Jobs not visible in Payload admin
  • RMM service only — not shared with Payload
MITFree
n8n
Visual workflow automation, 400+ integrations
Self-hostable visual workflow builder. Native Directus trigger node, Stripe, Xero, 3PL integrations. Right for complex cross-system workflows that neither Payload Jobs nor BullMQ was designed for. ERP integration layer.
PROS
  • 400+ pre-built integrations
  • Visual workflows non-developers can edit
  • Replaces custom webhook glue code
  • Self-hostable, fair-code license
CONS
  • Fair-code (sustainable use) license — check terms
  • Another service to operate
  • Not suited for high-frequency jobs
Fair-codeFree self-host
Temporal
Durable workflow engine, long-running processes
Durable workflows that outlive process restarts. Sleep for days, retry individual steps, exactly-once execution. Right for complex ERP approval chains, multi-day provisioning workflows. Overkill for basic queue jobs.
PROS
  • Workflows survive server restarts
  • Guaranteed exactly-once execution
  • Multi-day sleep, compensation patterns
  • Full audit trail of every workflow step
CONS
  • Significant operational complexity
  • Overkill for simple triggers/jobs
  • MIT but cloud offering is paid
MIT
Decision: Payload Jobs for management-plane triggers (low-frequency, needs audit trail). BullMQ in NestJS for RMM telemetry pipeline (high-frequency, Redis-backed). n8n for cross-system integration workflows (Stripe, Xero, 3PL). Temporal only when genuinely long-lived durable ERP workflows emerge.

Code-defined migrations + zero-downtime DDL
Drizzle generates SQL migration files from TypeScript schema changes (platform schema). pgroll handles runtime user-schema DDL changes (workspace object/field additions) with zero-downtime expand/contract pattern and instant rollback.
PROS
  • Drizzle: typed, version-controlled platform schema
  • pgroll: zero-lock DDL for runtime field additions
  • Both serve old+new schema simultaneously during migration
  • Instant rollback at any point
  • Twenty CRM uses pgroll — proven pattern
CONS
  • pgroll is a Go binary to operate
  • Drizzle + pgroll are separate mental models
  • Multi-tenant migrations need per-workspace execution
Apache 2.0Free

Layer 13 — Message Transport

MQTT Broker / Event Bus

Mosquitto
EPL-2.0, lightweight, the standard MQTT broker
Written in C, minimal footprint (~150 KB binary), handles hundreds of thousands of concurrent connections on modest hardware. The default choice for MQTT infrastructure. Runs as a Docker container or system service. Supports MQTT 5.0, TLS, WebSockets, persistent sessions, and QoS 0/1/2. The de-facto standard for agent-to-broker telemetry at RMM scale.
PROS
  • Industry standard — every MQTT client tested against it
  • Minimal resource footprint, single binary
  • MQTT 5.0, QoS 0/1/2, persistent sessions
  • TLS + WebSocket transport built in
  • Simple config file — no UI needed
CONS
  • EPL-2.0 (Eclipse license) — check distribution terms
  • No built-in clustering (needs bridge config)
  • No built-in auth UI — manage via config or plugin
  • Single-node by default — Redis needed for HA
EPL-2.0Free
EMQX
Apache 2.0, clustered, 100M+ connections
Erlang-based, horizontally scalable MQTT broker with built-in dashboard, rule engine, and webhook integration. Handles 100M+ concurrent connections in cluster. The right choice if you're building a multi-tenant SaaS platform offering RMM as a service at scale. Community edition is Apache 2.0; Enterprise adds paid features.
PROS
  • Apache 2.0 community edition
  • Built-in rule engine — route/transform messages without code
  • Web dashboard for connection management
  • Native clustering — no external Redis needed
  • Built-in Prometheus metrics export
CONS
  • Heavier than Mosquitto — overkill for <10K devices
  • Erlang runtime — unfamiliar ops for most teams
  • Enterprise features (persistence, audit) are paid
Apache 2.0Community free
NATS
Apache 2.0, pub/sub + queue groups + streaming
Not MQTT-native but covers the same use case with a simpler protocol. Single Go binary, sub-millisecond latency, built-in clustering and JetStream (persistent streaming). NestJS has a native NATS transport adapter. If you're already running NestJS microservices, NATS as the message bus is cleaner than bridging MQTT → NATS internally.
PROS
  • Single Go binary, <20 MB, zero dependencies
  • JetStream: persistent, replayable message streams
  • NestJS native transport adapter
  • Built-in clustering and leaf nodes
  • Sub-millisecond latency
CONS
  • Not MQTT — agents must use NATS client, not MQTT
  • Custom protocol means no off-the-shelf MQTT agents
  • OTel Collector can't export to NATS natively
Apache 2.0Free
Decision: Mosquitto for the RMM MQTT broker. It's the standard, minimal, and every agent (OTel Collector, custom Go agent, third-party) speaks MQTT. Run in Docker with TLS. Scale to EMQX only when you need multi-tenant broker isolation or horizontal clustering above ~50K concurrent connections. NATS is the right internal microservice bus if you add more NestJS services communicating with each other — use MQTT externally (agents → broker) and NATS internally (broker → NestJS services).

Layer 14 — RMM: Telemetry Pipeline

Continuous Metrics Collection (CPU, Memory, Disk, Network)

OTel Collector (hostmetrics)
Apache 2.0, vendor-agnostic, Windows MSI installer
Runs as a Windows service (MSI), Linux daemon, or macOS launchd. Hostmetrics receiver collects CPU, memory, disk I/O, network I/O, and process stats at configurable intervals. windowseventlog receiver collects Event Viewer channels. windowsperfcounters receiver queries arbitrary WMI/Performance Counter data. Exports via OTLP to your NestJS ingestion service, which writes to TimescaleDB.
PROS
  • Apache 2.0 — completely open
  • Windows MSI installer, Linux native packages
  • windowsperfcounters: arbitrary WMI data via YAML config
  • windowseventlog: Event Viewer ingestion built in
  • YAML config — no code to deploy per customer
  • Vendor-agnostic — backend swap without agent change
CONS
  • Continuous metrics only — no ad-hoc SQL queries (use Fleet for that)
  • Config distribution needs Ansible or Fleet scripts
  • No built-in agent management UI (Fleet manages Fleet agents, not OTel)
  • Separate agent from FleetDM — two things to install per endpoint
Apache 2.0Free
Netdata Agent
GPLv3+, per-second metrics, ML anomaly detection
Per-second metrics with zero configuration auto-discovery. 800+ integrations. ML trains 18 unsupervised models per metric at the edge. Windows support (Server 2016+, Windows 10+). Parent-child streaming topology. Cloud dashboard is paid above 5 nodes; self-hosted parent nodes are free. Replaces OTel Collector for metrics if you want a richer built-in UI and anomaly detection without building it.
PROS
  • Per-second granularity, zero-config auto-discovery
  • Built-in ML anomaly detection on every metric
  • Windows + Linux + macOS native agents
  • Parent node aggregation for fleet-wide view
  • No need to build dashboard charts from scratch
CONS
  • GPLv3+ — check distribution implications
  • Cloud SaaS required above 5 nodes for central management
  • Less flexible pipeline than OTel Collector
  • Third agent alongside FleetDM + possibly OTel
GPLv3+Agent freeCloud: paid >5 nodes
Custom Go Agent + MQTT
Build-your-own, full control
A small Go binary using gopsutil for system stats + golang WMI bindings for Windows-specific data, publishing to Mosquitto via MQTT. Full control over data model, heartbeat logic, and command channel. NestJS subscribes via @nestjs/microservices MQTT transport. Higher build cost but no third-party agent dependency.
PROS
  • Full control over telemetry schema and cadence
  • Single binary handles both telemetry push and command receive
  • No third-party agent on customer endpoints
  • gopsutil: cross-platform, well-maintained
CONS
  • Weeks of build time vs. using OTel Collector
  • Code signing, auto-update, distribution overhead
  • Duplicates what OTel Collector already does
  • No built-in anomaly detection or auto-discovery
MIT (gopsutil)Build cost only
Decision: OTel Collector for continuous metrics (CPU/mem/disk/network/WMI via windowsperfcounters/Event Log). FleetDM + osquery for inventory, software, processes, policies, and ad-hoc queries — these two serve different data shapes and do not overlap. Distribute the OTel Collector config per endpoint via Ansible (Linux) and Action1/Fleet scripts (Windows). The custom Go agent is only justified if you need a bidirectional command channel to endpoints that FleetDM's script execution doesn't cover — start without it, add only if that gap is real.

Layer 15 — RMM: Device Queries & Inventory

osquery Integration — What It Covers vs What It Doesn't

FleetDM + osquery (built-in tables)
MIT core — inventory, policies, software, compliance
osquery exposes the OS as an SQL database. Built-in tables cover installed software (programs table on Windows, apps on macOS), running processes, listening ports, user accounts, scheduled tasks, startup items, Windows registry, system info, certificates, browser extensions, and Disk Encryption status. Fleet adds vulnerability scanning (CVE matching against NVD), policy enforcement, software deployment, and GitOps-style YAML configuration.
PROS
  • SQL interface to any enrolled endpoint in <30s
  • programs / apps tables: full software inventory
  • Scheduled queries: run SQL on all endpoints on cron
  • Live queries: ad-hoc SQL during incident response
  • CVE scanning: matches software inventory against NVD
  • Fleet MCP server: Claude Code can query live endpoints
  • Webhook push: policy failures, new CVEs, host offline
CONS
  • Not designed for continuous high-frequency metrics (use OTel)
  • Query results not automatically time-series — point-in-time snapshots
  • MySQL + Redis infrastructure required to self-host Fleet
  • Custom extensions need TUF server for distribution
MIT coreFree
osquery Custom Extensions
Go/Python extensions for WMI-specific data
osquery's standard tables cover ~90% of Windows monitoring needs via Windows APIs. Custom extensions (Go or Python) add virtual tables for data osquery doesn't have natively — specific WMI classes, hardware sensors, custom application state. Fleet supports distributing custom extensions via a custom TUF update server. The Mac Admins community publishes several ready-to-use Windows extensions.
PROS
  • Virtual tables — query extension data with same SQL interface
  • Go or Python extensions, well-documented API
  • Community extensions available (Mac Admins osquery Slack)
  • Fleet distributes via TUF server — centrally managed
CONS
  • TUF update server needed for Fleet distribution
  • Extension code must be signed for production deployment
  • Still point-in-time queries, not streaming
Apache 2.0Free
Data shape split: FleetDM = what is on the endpoint (inventory, posture, compliance, software, vulnerabilities). OTel Collector = how the endpoint is performing over time (CPU%, memory%, I/O rates, event log stream). Both write to your backend — Fleet via REST API/webhooks to Payload, OTel via OTLP to NestJS → TimescaleDB. Never use Fleet for continuous time-series metrics and never use OTel Collector for software inventory or policy compliance.

Layer 16 — RMM: Configuration Management

Infrastructure Configuration, Scripts & Scheduling

Ansible + Semaphore
GPL-3.0 + MIT — playbooks + lightweight web UI
Ansible playbooks define desired configuration state as YAML code in version control. Semaphore (MIT) provides a web UI with RBAC, job scheduling, inventory management, and a REST API your Payload backend can call to trigger playbook runs programmatically. Ansible's agentless model (SSH on Linux, WinRM on Windows) means no additional agent to install alongside FleetDM and OTel Collector.
PROS
  • Agentless — no extra agent on endpoints
  • Playbooks in git — version controlled, peer-reviewed, CI/CD
  • Semaphore REST API: Payload backend triggers playbook runs
  • Handles complex state: IIS config, registry, service state, firewall rules
  • Idempotent — safe to run repeatedly
  • Huge module library (thousands of community modules)
CONS
  • WinRM config required on Windows (not always enabled)
  • Not designed for ad-hoc script execution (use Fleet scripts for that)
  • Semaphore is lighter than AWX — fewer features
  • Ansible Galaxy modules vary in quality and maintenance
GPL-3.0Semaphore: MITFree
AWX (Ansible Tower upstream)
Apache 2.0, full-featured Ansible web platform
The upstream open-source version of Red Hat Ansible Automation Platform. Richer than Semaphore: workflow templates, survey forms, credential management, RBAC. Kubernetes-native deployment (Operator). The right choice if you need Ansible at enterprise scale with multiple teams and approval workflows.
PROS
  • Workflow templates with approval gates
  • Survey forms for parameterized playbook runs
  • Enterprise RBAC and credential vault
  • REST API richer than Semaphore's
CONS
  • Kubernetes-native — heavier to self-host than Semaphore
  • Overkill for a single team running RMM playbooks
  • Longer setup time than Semaphore
Apache 2.0Free
Fleet Scripts (osquery scripting)
MIT — ad-hoc script execution via Fleet
Fleet can execute PowerShell, bash, and Python scripts on any enrolled endpoint via the REST API or the Fleet UI. The script runs once, immediately, and returns output. Right for ad-hoc remediation (restart a service, clear a cache, kill a process) that doesn't need Ansible's configuration-state model. Script library stored in Fleet, versioned in git via GitOps YAML.
PROS
  • No extra infrastructure — Fleet already installed
  • Results returned immediately via REST API
  • Script library in Fleet GitOps YAML repo
  • Works without WinRM (Fleet agent handles execution)
CONS
  • Run-once, not idempotent configuration state
  • No complex dependency management (Ansible roles do this)
  • Not suitable for multi-step infrastructure provisioning
MITFree
Decision: Fleet scripts for ad-hoc one-off execution (no WinRM needed, immediate results). Ansible + Semaphore for configuration-state management (IIS, registry, firewall, recurring enforcement). AWX only if you need multi-team approval workflows. The Payload backend calls Semaphore's REST API to dispatch Ansible jobs and receives webhook results back — no manual CLI needed from the dashboard.

Layer 17 — Queuing Architecture

Job Queues by Data Shape and Frequency

The queuing decision is not one choice — it's three tiers based on frequency, durability, and who needs to see the results.
Payload Jobs Queue (Tier 1)
Postgres-backed — low-freq, auditable, management-plane
Postgres-backed with admin UI visibility. afterChange hooks enqueue jobs. Jobs tracked in database with retry semantics, visible to admins. Right for: billing triggers, onboarding sequences, compliance report generation, scheduled software inventory snapshots, alert digest emails. Cadence: minutes to hours between runs per job.
PROS
  • Jobs visible in Payload admin UI
  • Postgres — no extra Redis dependency
  • Typed tasks with Zod input validation
  • Cron scheduling, retry with backoff
  • Integrated with afterChange hooks
CONS
  • Postgres polling — not for sub-second triggering
  • Not suited for thousands of jobs per minute
  • autoRun polling interval minimum ~1 min
MITFree
BullMQ + Redis (Tier 2)
Redis-backed — high-freq, RMM telemetry processing
Redis-backed via @nestjs/bullmq in the NestJS RMM service. Handles millions of jobs/day. Right for: OTel telemetry ingestion from endpoints (write to TimescaleDB), Fleet webhook processing (device offline, policy failure), Action1 patch completion events, alert condition evaluation against TimescaleDB. Cadence: seconds between runs, thousands per minute at scale.
PROS
  • Millions of jobs/day with concurrency control
  • Priority queues — critical alerts before routine ingestion
  • Rate limiting, deduplication, dead letter queues
  • Bull Board UI for queue monitoring
  • @nestjs/bullmq first-class NestJS integration
CONS
  • Redis dependency to operate and monitor
  • Jobs not visible in Payload admin
  • RMM NestJS service only — not shared with Payload
MITFree
Temporal (Tier 3)
MIT — durable, long-running ERP workflows
Workflows that outlive process restarts — sleep for days, retry individual steps, exactly-once execution, full audit history. Right for multi-step provisioning (new client onboarding spanning days), ERP approval chains (PO → approval → dispatch → invoice), or compensation workflows (if step 3 fails, undo steps 1 and 2). Not for routine queue work — add only when a workflow needs durability across failures.
PROS
  • Workflows survive server restarts and crashes
  • Individual step retry without restarting entire workflow
  • Saga pattern / compensation workflows native
  • Full audit timeline of every step
CONS
  • Significant operational complexity
  • Overkill for anything below minutes-long workflows
  • Adds another service to the infrastructure
  • Cloud (Temporal Cloud) is paid; self-hosted is complex
MIT
Decision: All three tiers serve distinct purposes and can coexist. Payload Jobs for management-plane triggers. BullMQ in NestJS for high-frequency telemetry and RMM event processing. Temporal deferred until a workflow genuinely needs durability across multi-day or multi-step compensation logic — introduce it for the ERP onboarding/provisioning use case when that arises.
